# 05. コンテンツ制作フローの自動化（ブログ・SNS連携）

> このドキュメントで決めること：**テーマ出しから SNS 投稿までを、どこまで機械に任せ、どこは人がやるか。**

最終更新：2026-09-22

---

## 1. 目指す制作フロー

```
  ①テーマ      ②壁打ち      ③ブログ化     ④HPに反映
  ストック  →  （AI）   →   （原稿）  →   （自動）
                                │
                                ├─→ ⑤画像化（自動）──→ Instagram / X
                                │
                                └─→ ⑥動画化（半自動）─→ Instagram / YouTube
```

**原本はブログ記事1本。** そこから画像・動画・SNS投稿文を派生させる。
逆流（SNSに書いたものをブログに戻す）はしない。原本が2つになると破綻する。

### みらいごとラボ方式との違い

| | みらいごとラボ（現行） | タカヤ（構想） |
|---|---|---|
| 原本 | YouTube 動画 | ブログ記事 |
| 派生 | 動画 → インスタ用に編集 | 記事 → 画像／動画 → SNS |
| 自動化の余地 | 動画編集が人の作業。切り出しの判断が肝 | **テキストが原本なので自動化しやすい** |

テキストが原本のほうが機械に渡しやすい。タカヤの構想のほうが自動化と相性がいい。

## 2. 工程ごとの自動化の可否（結論）

| # | 工程 | 自動化 | 実現方法 | 難易度 |
|---|---|---|---|---|
| ① | テーマのストック | **半自動** | リポジトリにテーマ一覧を置く。検索キーワードや問い合わせ内容から AI が候補を出す | 低 |
| ② | 壁打ち | **半自動** | AI との対話。ここは人が判断する工程として残す | 低 |
| ③ | ブログ原稿化 | **半自動** | 壁打ちの結果から下書き生成 → 人が確認 → CMS へ入稿 | 低 |
| ④ | HP に反映 | **完全自動** | CMS の Webhook → サイト再ビルド。コード0 | 低 |
| ⑤ | 画像化 | **完全自動** | テンプレートに文字を流し込んで PNG 生成 | **中** |
| ⑥ | 動画化 | **半自動** | 下記 4-6 参照。ここだけ性質が違う | 高 |
| ⑦ | X に投稿 | **完全自動** | X API v2 | 中 |
| ⑧ | Instagram に投稿 | **完全自動（条件付き）** | Instagram Graph API。画像が自動生成できる前提なら成立する | 中〜高 |

**⑥の動画化だけが明確に重い。** ①〜⑤・⑦⑧は現実的な工数で組める。

## 4. 各工程の作り方

### 4-1. ① テーマのストック

やること：思いついたテーマを1箇所に貯める。ネタ切れで止まるのが一番多い失敗。

| 置き場所の案 | 向いている場合 |
|---|---|
| このリポジトリの `docs/blog-themes.md` | GitHub を触る運用に慣れている場合 |
| スプレッドシート | 現場の人も書き込む場合 |
| CMS の「下書き」ステータス | 記事と同じ場所で管理したい場合 |

AI に候補を出させる材料：

- Search Console の検索クエリ（**実際に検索されている言葉**。一番強い材料）
- 問い合わせ・電話でよく聞かれること
- 季節もの（車検、タイヤ交換、バッテリー、猛暑・積雪前の点検など）
- 既存161本のうち、アクセスのある記事の続編

### 4-2. ② 壁打ち・③ ブログ原稿化

**ここは自動化しない。** AI に丸投げした原稿は、車屋の一次情報（実際の作業事例・価格感・地域性）が抜け落ちて、どこにでもある記事になる。検索でも評価されない。

現実的な形：

1. テーマを選ぶ（人）
2. AI と壁打ちして構成を固める（対話）
3. AI が下書きを出す
4. **人が一次情報を足す**（実際の事例、写真、価格、作業時間）← ここが価値の源
5. CMS に入稿・公開（人がボタンを押す）

入稿だけを自動化することもできる（CMS の API に投げる）が、**公開ボタンは人が押す形を残す**。
誤りがそのまま HP と全 SNS に拡散する事故を防ぐため。

### 4-3. ④ HP に反映

| 工程 | 仕組み | 実装量 |
|---|---|---|
| 記事を書く | microCMS の管理画面（ブラウザ） | 0 |
| HP に反映 | microCMS の Webhook → Cloudflare Pages の Deploy Hook | **設定のみ・コード0** |

公開ボタンを押すと数分で HP に載る。**ここはコードを1行も書かずに実現できる。**

Blogger を原本にする場合は、Blogger に Webhook がないため定期実行（1日2回など）で取りに行く形になり、
反映が最大で半日遅れる。この点でも HP 原本のほうが素直。

### 4-4. ⑤ 画像化（ここが要）

**仕組み**：記事のタイトル・要点を、デザインテンプレート（HTML/CSS）に流し込んで PNG を書き出す。
ヘッドレスブラウザでスクリーンショットを撮る方式が一番確実で、デザインの自由度も高い。

生成するもの：

| 用途 | サイズ | 内容 |
|---|---|---|
| Instagram（正方形） | 1080×1080 | 1枚目＝タイトル。2〜5枚目＝要点のカルーセル |
| Instagram（縦） | 1080×1350 | フィードで面積を取れる |
| X | 1200×630 | タイトル＋サイト名 |
| OGP（HPのシェア用） | 1200×630 | 同上。04-tech-and-ops.md 7章のチェック項目 |

テンプレートは 03-design-system.md の色・書体に合わせる。ここを守ると投稿が並んだときに統一感が出る。

**この工程の自動化が、全体で一番効く。** Instagram で毎回デザインを作る手間が消える。

**【要記入】**：1記事あたり何枚のカルーセルにするか（3枚／5枚／可変）

### 4-5. ⑥ 動画化

ここだけ性質が違うので、正直に書く。

| 案 | 内容 | 現実性 |
|---|---|---|
| A. 画像スライドショー | 4-4 の画像を繋いで、BGM・字幕を付けた15〜30秒の動画 | **自動化できる。まずはこれ** |
| B. 既存YouTube動画の切り出し | 文字起こし → AI が見どころを抽出 → 縦型に切り出し | 半自動。元動画がある場合に有効 |
| C. テキストから動画を生成 | 記事から動画そのものを作る | **品質が読めない。おすすめしない** |

みらいごとラボは元動画があるので B が効く。タカヤは元動画がまだないので、**A から始めるのが現実的。**

A でも「タイトル → 要点3つ → 店舗情報」という15秒の縦動画は自動で作れる。
リール枠を埋める用途としては十分に機能する。

**【要記入】**：タカヤで動画（YouTube等）を撮る予定はあるか

### 4-6. ⑦⑧ SNS への反映

| | 投稿できるもの | 備考 |
|---|---|---|
| X | テキスト＋画像 | 「タイトル＋URL＋画像1枚」が基本形 |
| Instagram | 画像（最大10枚のカルーセル）／リール／ストーリーズ | **テキストのみの投稿は不可**。必ず画像か動画が要る |

Instagram の API は「公開URLに置いてある画像」を指定する方式なので、
4-4 で生成した画像を Cloudflare R2 等に置けば、そのまま繋がる。

## 5. Instagram 自動投稿についての判断の修正

**前回「おすすめしない」と書いたが、判断を修正する。**

前回の理由は「ブログ本文を機械的に流しても、写真が主役の Instagram では反応が取れないから」だった。
**4-4 で画像を自動生成する構想なら、この前提が変わる。** カルーセル画像を作って投稿するなら成立する。

ただし残る負荷は変わらないので、そこは正確に：

| 項目 | 内容 |
|---|---|
| 必須条件 | **プロアカウント**（ビジネス／クリエイター）であること |
| 必要なもの | Meta の開発者アプリ登録、アクセストークン、場合によりビジネス認証・アプリ審査 |
| 画像の渡し方 | ローカルファイルは直接アップロードできない。**公開URLの画像**を指定する |
| 投稿数の上限 | 24時間あたり25件程度【要確認】 |
| **最大の注意点** | アクセストークンが**約60日で期限切れ**。自動更新を組まないと、ある日静かに投稿が止まる |

**落としどころ**：画像の生成までを自動、投稿ボタンは人。
これなら Meta の審査もトークン管理も不要で、手間はほぼ同じだけ減る。
運用が回り始めてから、投稿まで自動化するか判断すればいい。

## 6. 各サービスの技術的な条件

### 6-1. X（旧 Twitter）

| 項目 | 内容 |
|---|---|
| 方法 | X API v2 の投稿エンドポイント |
| 必要なもの | X 開発者アカウント、アプリ登録、APIキー |
| 無料枠 | 月あたりの投稿数に上限あり（数百件程度）【要確認：最新の枠を公式で確認】 |
| 月に数本の告知 | 無料枠で十分に収まる |
| **画像付き投稿** | メディアアップロードが無料枠で使えるか【要確認】。使えない場合はテキスト＋URLのみ |

### 6-2. Google ビジネスプロフィール

| 項目 | 内容 |
|---|---|
| 方法 | Business Profile API の投稿機能 |
| 条件 | API 利用には申請・審査が必要【要確認】 |
| 現実的な運用 | 当面は手動。ただし車の整備・販売業では**来店への影響が大きい**ので、更新自体は止めない |

4-4 で生成した画像はそのまま使い回せるので、手動でも投稿の手間は小さくなる。

### 6-3. YouTube

動画を始める場合、YouTube API で公開まで自動化できる。
ただし**サムネイルとタイトルで再生数がほぼ決まる**ため、そこは人が判断する工程として残す。

## 8. 進め方（段階を分ける）

| フェーズ | やること | 前提 | 効果 |
|---|---|---|---|
| 0 | テーマのストック場所を決めて貯め始める | 今すぐ可能 | ネタ切れで止まらなくなる |
| 1 | 各SNSの**予約投稿機能**を使い始める | 今すぐ可能・コード不要 | 投稿作業をまとめられる |
| 2 | 記事 → HP 反映（自動） | 新 HP の公開 | 記事が自社ドメインの資産になる |
| 3 | 記事 → **画像の自動生成** | フェーズ2 | **ここが一番効く** |
| 4 | X に自動投稿 | フェーズ3 | 告知を書く手間が消える |
| 5 | Instagram に自動投稿 | フェーズ4 ＋ トークン運用の覚悟 | 投稿ボタンを押す手間が消える |
| 6 | 動画化 | 運用が回ってから | リール枠が埋まる |

**フェーズ3までで、体感の手間はかなり減る。** フェーズ5・6は「やらない」という結論も十分あり得る。
先にフェーズ0〜3で手応えを見る。

## 9. 自動化する前に決めておくこと

- [ ] 誤字のまま全SNSに出る事故を防ぐため、**公開前に人が確認する工程を1つ残す**
- [ ] 自動投稿が止まったことに気づける仕組み（失敗時に通知を飛ばす）
- [ ] APIキー・トークンは GitHub のコードに書かない（Actions の Secrets／Cloudflare の環境変数に置く）
- [ ] 各SNSアカウントの管理者が誰か。退職・引き継ぎで止まるのが一番多い失敗
- [ ] 投稿文のテンプレート（タイトル／URL／ハッシュタグの形）
- [ ] 画像テンプレートのデザイン（→ 03-design-system.md に合わせる）

## 11. 見送り案

| 案 | 見送る理由 |
|---|---|
| AI に原稿を丸投げして自動公開 | 一次情報が抜けた記事は検索でも読者にも評価されない。人が事例と写真を足す工程は残す |
| 記事から動画そのものを生成（4-5 のC案） | 品質が読めない。画像スライドショー（A案）で足りる |
| 全SNSを完全自動化する | 1箇所の誤りが全チャネルに拡散する。確認工程を1つ残すほうが安全 |
| 有料の投稿代行ツール（Buffer 等）を入れる | 月額が継続的にかかる。まずは各SNS標準の予約投稿で足りるか見てから |
| ブラウザ側で RSS を読んで HP に表示する | 検索エンジンに本文が載らず、SEO の資産にならない |
| SNS に書いたものをブログに戻す | 原本が2つになる。流れは一方向に保つ |
